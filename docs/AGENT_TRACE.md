# Agent 运行轨迹设计：让老师看到「它在做事」，而不是一个网页表单

> 你的担心是对的：如果前端只有「上传 → 生成 → 列表」，它就是一个 Web 应用。
> Agent 和 Web 应用的区别不在界面，而在**运行时是否有：计划、工具调用、观察结果、失败重试、人工确认、可回放的中间状态**。
> 这份文档定义这些状态如何产生、如何展示、如何写进报告。

---

## 1. 一句话原则

> **前端不是 Agent 本身，前端是 Agent 状态的实时投影。**

所有步骤必须由后端编排器真实执行并发出事件；前端只负责渲染事件流。**不允许前端写死进度条或假装在跑。**

---

## 2. 运行时结构

```
用户输入
  ↓
Planner（制定计划：这次需要哪些步骤）
  ↓
Executor（逐步执行）
  ├── Tool: schema_validator / llm_extract / sqlite / tfidf_svm
  ├── Tool: logreg_ranker / tier_rule / http_checker
  ├── Tool: docx_template / fact_checker / exporter
  ↓
Observer（每步输出摘要 + 置信度 + 错误）
  ↓
Policy（继续 / 重试 / 回退 / 请求人工确认）
  ↓
Trace（完整事件流 + 产物，落盘可回放）
```

**关键点**：

- Planner 先输出计划，用户能看到「它打算做几步、每步为什么」；
- 每步有 `why`（为什么做）、`tool`（用什么）、`input/output`（吃了什么、吐了什么）；
- 失败不是弹个错，而是进入 `retry / fallback / human_gate`；
- 整个 trace 落盘，报告和演示都能复现。

---

## 3. 事件 schema

每个步骤产生一条或多条事件：

```json
{
  "run_id": "20261123-203512-a1b2",
  "seq": 6,
  "step_id": "rank_jobs",
  "title": "匹配排序",
  "status": "done",
  "why": "用 ML 给候选岗位打分，决定先看哪些",
  "tool": "logreg_ranker",
  "model": "logreg-v1 + bge-small-zh",
  "input_summary": "画像 r01 × 候选 128 条",
  "output_summary": "Top-10，最高分 0.82，最低 0.41",
  "confidence": 0.78,
  "retry_count": 0,
  "human_gate": false,
  "started_at": "2026-11-23T20:35:16+08:00",
  "ended_at": "2026-11-23T20:35:17+08:00",
  "duration_ms": 842,
  "detail": {
    "features": {"skill_cov": 0.71, "bge_cos": 0.63},
    "top_k": [{"job_id": "j001", "score": 0.82}]
  },
  "error": null
}
```

| 字段 | 作用 |
|---|---|
| `run_id` | 一次运行唯一 ID，用于回放/报告 |
| `seq` | 顺序号，前端按它排序 |
| `step_id` / `title` | 机器名 + 人话 |
| `status` | `pending / running / done / error / skipped / waiting_human` |
| `why` | **最重要**：为什么做这一步，对应报告里的「流程说明」 |
| `tool` / `model` | 用了什么工具/模型，对应 Skills 复用 |
| `input_summary` / `output_summary` | 一句话说清吃了什么、吐了什么 |
| `confidence` | 置信度，低于阈值转人工 |
| `retry_count` | 重试次数，展示失败处理 |
| `human_gate` | 是否要用户确认 |
| `duration_ms` | 真实耗时，不是假进度 |
| `detail` | 中间产物（特征、Top-k、SQL、错误堆栈） |
| `error` | 失败原因 |

## 4. 流水线：12 步，每步都要能在前端讲清

| # | step_id | 做什么 | 工具 | 输出 | 失败处理 |
|---|---|---|---|---|---|
| 0 | `plan` | 根据输入决定执行哪些步骤 | Planner（LLM/规则） | 计划列表 | 输入不足 → 只跑采集 |
| 1 | `intake` | 校验必填字段、脱敏 | schema_validator | 缺失项清单 | 缺关键项 → 等待补全 |
| 2 | `normalize` | 散装文本 → 事实库 JSON | llm_extract + JSON Schema | `facts.json` | 解析失败 → 重试/手填 |
| 3 | `load_jobs` | 读取岗位库、按城市/方向过滤 | sqlite | 候选 N 条 | 0 条 → 放宽条件提示 |
| 4 | `classify_family` | 岗位族分类（ML） | TF-IDF + LinearSVC | 每类概率/标签 | 低置信度 → `未分类` |
| 5 | `rank_jobs` | 简历–岗位匹配排序（ML） | logreg / LambdaRank | Top-k + 分数 | 模型缺失 → BM25 兜底 |
| 6 | `group_tiers` | 按公司表分大/中/小 | tier_rule | 三档列表 | 公司未标注 → `未分层` |
| 7 | `check_links` | 核验链接可用性 | http_checker | `ok/login/dead` | 死链 → 公司主页/搜索页 |
| 8 | `tailor_resume` | 按 JD 重排/改写 bullet | template + LLM | 定制简历 JSON | 超一页 → 自动裁剪 |
| 9 | `verify_facts` | 数字/公司/时间回查 | rule + LLM | 通过/拦截 | 不通过 → 回退基础版 |
| 10 | `export` | DOCX/PDF、打招呼语 | python-docx | 文件 | 导出失败 → Markdown 兜底 |
| 11 | `track` | 记录「已投」、跟进提醒 | sqlite | 投递记录 | 写入失败 → CSV 兜底 |

**注意**：`classify_family` 和 `rank_jobs` 是机器学习步骤，前端要显示模型名、特征、指标入口；`group_tiers` 是规则，不要伪装成 ML。

### 每个步骤卡片显示

- 状态点（灰/蓝/绿/红/橙）；
- 标题 + 真实耗时；
- `why` 一句话；
- 工具/模型标签；
- 置信度（如有）；
- 展开后看输入/输出/原始 JSON。

### 三个必须有的区域

1. **计划区**：运行前展示「我打算做这 12 步」，让老师看到规划；
2. **工具调用区**：显示 SQL、模型、HTTP、模板引擎的调用记录；
3. **人工确认区**：定制简历/标记已投前，弹出确认，记录用户选择。

## 6. 如何证明「不是普通 Web 应用」

| 普通 Web 应用 | 本项目 |
|---|---|
| 表单提交 → 后端函数 → 页面 | Planner 先规划 → Executor 逐步执行 → Observer 记录 → Policy 重试/回退 |
| 失败就报错 | 失败有 `retry / fallback / human_gate`，trace 里能看到 |
| 前端不知道中间状态 | 每个中间产物（facts、候选、分数、链接状态）都可查看 |
| 结果不可复现 | `run_id` + trace JSON 可回放 |
| 模型是黑盒 | 显示模型名、特征、置信度、指标入口 |
| 用户只能看最终简历 | 用户能看到「为什么推荐这个岗位、为什么删了这条 bullet」 |

**演示时重点讲三件事**：

1. 它先规划再执行（00 计划）；
2. 它调用工具并观察结果（SQL 查了多少条、链接是死是活）；
3. 它会失败、重试、请求人工确认（至少演示一次失败分支）。

## 7. 实现方式（Streamlit 版）

```python
# 伪代码
bus = EventBus(run_id)
agent = ResumeAgent(bus=bus)
for event in agent.run(payload):      # 生成器，每步 yield 事件
    render_timeline(st.session_state.events)
    render_detail(event)
```

- 用 `st.empty()` 占位，逐步更新；
- 用 `time.perf_counter()` 记录真实耗时；
- 未实现的步骤标 `skipped` 并写原因，**不要假装完成**；
- trace 落盘 `runs/{run_id}.json`，提供「回放」下拉框；
- 如果后续换 FastAPI + React，事件流不变，只换渲染层。

## 8. 演示脚本（3–5 分钟）

1. 输入散装信息 → 点「运行 Agent」；
2. 00 计划：展示 12 步和每步作用；
3. 02 画像：展示抽取的事实、缺失项、脱敏结果；
4. 04 分类：展示岗位族分布和低置信度样本；
5. 05 排序：展示 Top-10、匹配分、匹配/缺失技能；
6. 06 三档：展示大/中/小各 5 个，说明分层是规则；
7. 07 链接：演示一个 `dead` 链接自动切公司主页；
8. 08 定制：展示基础版 vs 定制版 diff；
9. 09 校验：演示一条编造数字被拦截；
10. 10 导出：下载 DOCX/PDF；
11. 11 追踪：点「标记已投」，看板出现记录；
12. 导出 trace JSON，说明可回放。

---

## 9. 反模式（不要做）

- 前端写死 `st.progress` 或 `sleep` 假装在跑；
- 只有一个聊天框，所有步骤藏在后端日志；
- 把「调用一次 LLM」叫 Agent；
- 把公司分层说成 ML；
- 失败时只弹「出错了」，没有 trace；
- 演示只走成功路径，不给失败分支。
