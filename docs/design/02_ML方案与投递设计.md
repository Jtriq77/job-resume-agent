### 1.2 M1：简历–岗位匹配排序（首选，建议单点打透）

#### 为什么它最容易拿高分

1. **课程明确列了「检索排序」**，方法合法性无需辩护；
2. **天然有强基线**：BM25、TF-IDF、向量相似度，对比公平；
3. **指标标准**：NDCG@5/10、Recall@5、MRR，评审一看就懂；
4. **可消融**：去掉技能特征、去掉语义特征、去掉学习排序，各有一条结论；
5. **直接驱动 Agent**：排序决定投哪个、改写哪些关键词，不是外挂 demo；
6. **可解释**：逻辑回归系数能回答「为什么推荐这个岗位」，正好对应评分标准里「解释判断依据」。

#### 任务定义（报告里必须写清）

给定简历 $r$ 与岗位 $j$，输出相关性等级 $\hat{y}\in\{0,1,2,3\}$ 或连续匹配分，并据此排序。

| 等级 | 含义 | 判定标准（标注 rubric） |
|---|---|---|
| 3 | 强匹配，优先投 | 硬性条件全满足；must-have 技能覆盖 ≥70%；有 1 段直接相关经历 |
| 2 | 可投，需小改 | 硬性条件全满足；技能覆盖 50–70%；有可迁移经历 |
| 1 | 弱匹配，需大改 | 硬性条件有 1 项风险；技能覆盖 <50%；或方向偏差较大 |
| 0 | 不匹配 | 硬性条件不满足（学历/年级/城市/到岗/专业限制）或方向完全不同 |

> **不要叫「录取概率」**。叫「投递相关性」或「匹配度」。前者需要真实标签，你没有；后者可人工标注、可复核。

#### 模型路线

```
BM25（基线）
  → TF-IDF 余弦（基线）
  → BGE 向量余弦（基线）
  → 逻辑回归（全特征，主模型）
  → LightGBM LambdaRank（排序学习，对比）
```

- **主模型用逻辑回归**：150 对样本，LambdaRank 容易过拟合；LR + L2 更稳，系数可解释。
- **LambdaRank 只作为对比**：如果它更好，是加分；如果不更好，也是结论（「小样本下点式分类优于列表式排序」），照样能写。
- **校准**：LR 输出做 Platt/isotonic 校准，分数才能当「置信度」用于低置信度转人工。

#### 特征（15–20 维，够用且可解释）

| 类别 | 特征 |
|---|---|
| 词法 | TF-IDF 余弦（jieba 分词）、字符 3-gram 余弦 |
| 检索 | BM25 分数 |
| 语义 | BGE 余弦（长 JD 分块池化） |
| 技能 | must-have 覆盖率、nice-to-have 覆盖率、技能 Jaccard |
| 硬性 | 学历满足、专业相关、城市匹配、到岗时间匹配 |
| 经历 | 实习/项目月数、量化成果 bullet 占比 |
| 质量 | 简历分节完整度、bullet 数、JD 长度/must-have 数 |

#### 实验矩阵（这是 20 分的核心）

| 组 | 配置 | 回答什么问题 |
|---|---|---|
| B1 | BM25 | 纯检索能做到多少 |
| B2 | TF-IDF | 经典文本相似度 |
| B3 | BGE | 纯语义 |
| B4 | LR（全特征） | 你的主模型 |
| B5 | LambdaRank | 排序学习是否更好 |
| A1 | LR − 技能特征 | 领域词典的贡献 |
| A2 | LR − BGE | 语义表示的贡献 |
| A3 | BM25 only（=B1） | 学习排序的净贡献 |
| A4 | LR − 硬性规则特征 | 结构化条件的贡献 |

- **验证**：留一简历交叉验证（每次留 1 份简历的全部岗位对），报告均值 ± 标准差。
- **补充**：30 对双人标注算 Cohen's κ；κ<0.6 就修 rubric 重标。
- **错误分析**：按「数据/表示/模型/提示词/工具/任务设计」六类归因，每类给 1–2 个例子。

#### 这个方案的边界（报告要主动写）

- 10 份简历、150 对，样本小，结论只能说明「在这个小测试集上」；
- 单一领域（数据/产品），跨领域泛化未验证；
- 标注带主观性，κ 值就是证据；
- 匹配度不等于录用率，不能承诺「投了就有面试」。

> **主动写局限，比被评审问出来更加分。**

### 1.3 M2：岗位族分类（次选，适合做「路由」而不是主菜）

**做什么**：JD → 岗位族（数据分析 / 产品经理 / 产品运营 / 算法 / 后端 / 其他）。

**课程点**：TF-IDF + 朴素贝叶斯 / 线性 SVM / 逻辑回归；Macro-F1、混淆矩阵、类别不平衡。

**价值**：
- 冷启动：简历还没上传时，先让用户选方向；
- 岗位地图：按族聚合，回答「我适合投什么」；
- 路由：不同族用不同的技能词典和改写模板。

**成本**：300–500 条 JD 打族标签。可以先用「标题关键词规则」预标，再人工抽检 100 条；但**报告里必须说明预标规则**，不能假装全人工。

**风险**：单独作为主 ML，会被评为「文本分类课程作业」，与「投递决策」关系弱。**只建议作为 M1 的上游路由，不建议单独扛 20 分。**

---

### 1.4 M3：JD 聚类岗位地图（最便宜的亮点，半天）

**做什么**：对 JD 向量做 K-Means，轮廓系数选 k，PCA/UMAP 可视化，人工给簇命名。

**课程点**：无监督学习、聚类、表示学习、模型选择。

**评估**：
- 轮廓系数（定量）；
- 簇纯度：用 M2 的族标签（若有）或人工抽检 5 条/簇（定性）；
- 用户可用性：3 位同学看「岗位地图」能否说出自己想投的簇（小样本定性）。

**价值**：演示好看，回答「我不知道投什么」；可作为 Streamlit 的一个页面。

**风险**：聚类本身不产生「任务结果」，单独撑不起 ML 分。**建议作为 M1 的可视化补充，时间够再做。**

---

### 1.5 M4：简历质量评分（不建议做主）

**做什么**：简历 → 1–5 分，或「缺量化/缺项目/格式混乱」多标签。

**课程点**：回归/多标签分类、特征工程、MAE/Spearman。

**问题**：
- 标签主观，2 人评分一致性可能很低；
- 与「投递决策」关系弱，更像简历润色工具；
- 4 天内标注 60 份简历不划算。

**结论**：可作为改写前的规则诊断（量化比例、STAR 完整度），**不要作为主 ML**。

---

### 1.6 M5：LLM 弱标注 + 蒸馏（冲亮点，风险高）

**做什么**：用 LLM 给 1000 对简历–JD 打相关性标签 → 训练逻辑回归/小模型 → 在 150 对人工金标准上评估。

**卖点**：
- 成本对比：LLM 逐对判断 vs 蒸馏小模型，成本降 90%+、时延降 10 倍；
- 课程点：弱监督、分类、模型评估、成本-效果权衡；
- 故事好：「不是所有判断都要调用大模型」。

**风险**：
- 评审可能质疑「用 LLM 标签训模型，再用人工标签评估」是循环论证；
- LLM 标签噪声大，需要人工金标准兜底；
- 4 天内做完 M1 + M5 很紧。

**结论**：**M1 在 11/25 晚跑通后再考虑**。做的话必须在报告里明确「LLM 只用于训练集弱标注，测试集全部人工标注」。

## 2. 「投递」重定义：不是点击提交，而是投递运营

### 2.1 你的担心是对的，但结论可以反过来

你说得对：**「生成投递包 + 自己点提交」如果只做到这一步，「投递」两个字确实撑不起来。**

但换个角度看，投递的真实工作量从来不是那 5 秒点击，而是：

```
发现岗位 → 判断能不能投 → 判断值不值得投 → 改简历 → 填平台表单
→ 写打招呼语 → 选渠道 → 提交 → 记录 → 跟进 → 复盘
```

**点击提交只占 5 秒，前后 40 分钟才是痛点。** Agent 把这 40 分钟压到 5 分钟，最后 5 秒留给用户确认——这不是功能缺失，而是**human-in-the-loop 的设计选择**。评分标准原文就要求「高影响结果必要时人工确认」，这个边界反而是加分项。

更重要的是：**平台格式要求不是障碍，而是工作量证据。** BOSS 直聘、领英、牛客的字段、字数、附件格式都不同，做一个「平台适配层」本身就是实打实的工程整合，正好对应「Skills 复用与工程整合 15 分」。

**结论**：不改题目，改定义。在报告里明确写：

> 本文将「投递」界定为**投递决策、投递资产准备、投递执行辅助与投递追踪**；真实平台提交由用户完成，原因是平台协议、账号安全与隐私边界。该边界是设计选择，不是功能缺失。

如果还担心字面意义，**加一个本地 mock 平台**，把「填写 → 检查 → 点击提交 → 状态变更」完整演一遍。这样「投递」的字面动作也保住了，且完全不碰真实平台。

### 2.2 七种实现方式（按性价比排序）

| # | 方式 | Agent 做什么 | 用户做什么 | 合规性 | 工作量 | 可评估指标 |
|---|---|---|---|---|---|---|
| 1 | **平台格式适配** | 按 BOSS/牛客/领英的字段、字数、附件要求生成不同版本投递包 | 选择平台 | 合规 | 0.5–1 天 | 字段合规率、字数超限率、导出成功率 |
| 2 | **资格门槛判定** | 抽取学历/年级/专业/到岗/城市/薪资等硬条件，判定「可投/风险/不可投」 | 确认 | 合规 | 0.3 天 | 100 条 JD 上的 Precision/Recall |
| 3 | **投递组合优化** | 从 N 个岗位中选本周投递的 k 个，兼顾相关性、多样性、截止时间 | 确认批次 | 合规 | 0.5 天 | 批次相关性、岗位族覆盖率、冗余度 |
| 4 | **渠道推荐** | 按公司类型/岗位族推荐官网/内推/BOSS/牛客/领英 | 选择 | 合规 | 0.2 天 | 人工评分、覆盖率 |
| 5 | **ATS 解析检查** | 导出 PDF 后再解析，检查招聘系统能读到哪些字段、缺什么 | 修正 | 合规 | 0.3 天 | 字段完整率（改模板前后） |
| 6 | **投递追踪 CRM** | SQLite 记录状态、时间线、跟进提醒、漏斗统计 | 更新状态 | 合规 | 0.3 天 | 记录完整率、重复率、跟进及时率 |
| 7 | **本地 mock 平台提交** | 模拟平台表单，自动填充，用户点击提交，写入数据库 | 点击确认 | 合规 | 0.3–0.5 天 | 端到端成功率、确认耗时 |
| 8 | 真实自动投递 | 浏览器自动化登录/填表/提交 | 无 | **高风险**：多数平台协议禁止自动化，有验证码/风控/封号风险，且难复现 | 2 天+ | 不建议 |

> 第 8 种为什么不做：BOSS 直聘、领英、牛客等**未见公开投递 API**；浏览器自动化通常违反用户协议，账号可能被封；演示时还需要真实账号和网络，复现性极差；把同学简历批量提交给第三方也有隐私问题。**课程项目做这个，风险远大于收益。**

### 2.3 推荐组合（4 天版）

**必做：1 + 2 + 6 + 7**（平台适配、资格判定、追踪 CRM、mock 提交）

**顺带做：5**（ATS 解析检查，作为 1 的验收环节，不单独占模块）

**选做：3 或 4**（时间够再加，11/26 下午决定）

**不做：8**

这样「投递」就有了四个可演示、可评估的环节，而不是一句空话。

### 2.4 演示脚本（录屏按这个走）

1. 上传简历 → 画像确认（展示 LLM 抽取 + 人工修正）；
2. 选目标「数据分析 / 上海」→ 排序 Top 10（展示匹配分、证据、缺失技能）；
3. 点开一个岗位 → 资格判定「可投」+ 差距 3 条；
4. 生成 BOSS 版和牛客版两套投递包（不同字段/字数）→ 本地文件夹可见；
5. 打开本地 mock 平台页 → Agent 自动填 8 个字段 → 用户检查 → 点击「提交」→ 状态变「已投」；
6. 追踪看板：本周投递漏斗、待跟进提醒；
7. **故意演示一次失败**：低置信度岗位提示「证据不足」，或事实校验拦截一条编造的数字。

第 7 步很重要：评分标准明确看「失败与安全处理」，一段失败演示比十张成功截图更有说服力。

### 2.5 报告里怎么写「投递」

- **定义**：投递 = 决策 + 资产 + 执行辅助 + 追踪；提交由人完成。
- **理由**：平台协议、账号安全、隐私、可复现性；引用各平台用户协议/帮助页（记录 URL 与日期）。
- **指标**：字段合规率、ATS 字段完整率、投递包完整率、确认耗时、追踪记录完整率。
- **边界**：不承诺「自动投递」；不存储平台账号密码；不批量提交。
- **标题建议**（保留「投递」但更准确）：
  1. **《面向应届生的简历定制与投递决策 Agent》**（推荐）
  2. 《人岗匹配驱动的简历定制与投递运营 Agent》
  3. 《求职投递助手：匹配、定制与追踪》

## 3. 数据素材：优先级、格式、数量

### 3.1 今天先收什么（按优先级）

```
JD 语料  >  简历  >  标注对  >  技能词典  >  平台字段规范  >  需求访谈
```

**原因**：JD 决定检索库和标注候选；简历是 query；标注是实验的地基；后面三项是加分项。

### 3.2 JD 语料（最重要）

| 项 | 要求 |
|---|---|
| 数量 | **120–150 条**（最低 80，理想 300） |
| 方向 | 数据分析 / 产品经理 / 产品运营 / 用户增长 / 商业分析为主，另加 20% 其他方向做负样本 |
| 类型 | 70% 校招/实习，30% 初级社招 |
| 长度 | 150–800 字，必须含「岗位职责 + 任职要求」 |
| 噪声 | 故意保留 15–20% 短 JD、模糊 JD、英文 JD，用于错误分析 |
| 来源 | 企业校招官网、高校就业信息网、天池招聘数据集、牛客/实习僧公开页面、自己收到的 JD 邮件 |
| 记录 | 每条记 `source_url`、`collected_at`、`license_note` |

**JSONL 格式（一行一条）**：

```json
{"jd_id":"jd_0001","title":"数据分析师（校招）","company":"某互联网公司","city":"上海","salary":"15-25K","education":"本科","experience":"应届","employment_type":"校招","family":"数据分析","raw_text":"岗位职责：...\n任职要求：...","source_url":"https://...","collected_at":"2026-11-24","license_note":"公开页面，仅课程研究使用"}
```

**采集注意**：
- 手动复制，不要写爬虫批量抓；尤其不要碰需要登录、验证码、付费的页面；
- 每条 3–5 分钟，150 条约 8 小时——**今晚先干 50 条**；
- 用数据集批量导入时，先核对许可证；天池数据集需看页面条款；
- 不要收录含真实 HR 姓名/电话的 JD。

### 3.3 简历（query）

| 项 | 要求 |
|---|---|
| 数量 | **6–8 份**（最低 5，理想 12） |
| 多样性 | 有实习/无实习、跨专业、数据/产品/运营方向、1 页/2 页、好/差各半 |
| 格式 | 原始 PDF/DOCX + 解析文本 + 结构化 JSON + 授权记录 |
| 脱敏 | 姓名→`[姓名]`；手机/邮箱/身份证/住址→删除；学校→`school_tier`（985/211/双非/海外） |
| 授权 | 微信文字/截图即可：「同意将我的简历用于《机器学习》课程项目，数据脱敏、仅本地实验、不公开原始文件」 |

**结构化 JSON 格式**：

```json
{"resume_id":"r01","school_tier":"211","degree":"本科","major":"信息管理","graduation_year":2026,"city_pref":["上海","杭州"],"skills":["SQL","Python","Tableau"],"experiences":[{"org":"[某电商公司]","role":"数据分析实习","start":"2026-03","end":"2026-08","bullets":["用 SQL 分析..."]}],"projects":[],"raw_text":"..."}
```

> **为什么要结构化**：ML 特征、资格判定、改写约束都依赖它；只靠原始文本，后面每一步都要重复解析。

### 3.4 标注对（实验地基）

| 项 | 要求 |
|---|---|
| 数量 | **100–150 对**（最低 60，理想 150） |
| 构造 | 每份简历 × 12–15 个岗位；刻意包含 0/1/2/3 各档 |
| 标注 | 0–3 四级；写理由；2 人独立标 30 对算 κ |
| 格式 | CSV：`pair_id,resume_id,jd_id,label,reason,annotator,ts` |
| 一致性 | κ<0.6 → 修 rubric，重标 10 对试标 |

**Rubric 锚例（写进报告附录）**：

- 3 分：JD 要求 SQL/Python/Tableau，简历有 SQL 项目 + Python 分析 + Tableau 看板，学历/城市/到岗全满足；
- 2 分：同上但缺 Tableau，只有 Excel 可视化；或专业不完全对口但技能覆盖高；
- 1 分：技能只覆盖 1/3，且无直接相关经历；但学历/城市满足；
- 0 分：要求 2027 届，你是 2026 届；或要求 5 年经验；或岗位在另一个城市且你不接受。

### 3.5 技能词典

| 项 | 要求 |
|---|---|
| 数量 | **150–250 个**技能/工具/证书 |
| 字段 | `skill_id, canonical, aliases_zh, aliases_en, category, importance, source` |
| importance | must / nice / optional（用于覆盖率加权） |
| 来源 | JD 高频词统计 + ESCO/O*NET（核对许可证）+ 人工补充 |
| 作用 | 同义词归一（「数据分析」vs「BI」）、覆盖率特征、差距诊断、改写关键词 |

### 3.6 平台字段规范

| 项 | 要求 |
|---|---|
| 数量 | **2 个平台**（BOSS直聘 + 牛客；有英文再加领英） |
| 字段 | `platform, field, required, max_len, format, notes, source_url, checked_at` |
| 来源 | 平台帮助页/实际投递页，**逐条打开确认**，不要凭印象填字数 |
| 用途 | 平台适配层、合规校验、演示 |

**JSON 示例（字数上限以实际页面为准）**：

```json
{"platform":"BOSS直聘","checked_at":"2026-11-24","source_url":"https://...","fields":[{"name":"期望岗位","required":true,"max_len":null,"format":"text"},{"name":"打招呼语","required":true,"max_len":null,"format":"text"},{"name":"附件简历","required":true,"format":"pdf"}]}
```

### 3.7 需求访谈（15 分证据）

问 3–5 位正在投递的同学，每人 5 分钟，记录原话：

1. 最近一次改简历花了多久？改了哪些部分？
2. 怎么判断一个岗位「值不值得投」？看哪几条？
3. 投递记录记在哪？有没有漏投/重复投？
4. 被拒后知道为什么吗？最想知道什么？
5. 如果只能帮你做一件事，你选：排序推荐 / 自动改写 / 投递追踪 / 面试准备？

**产出**：`docs/interviews.md`，匿名，含日期、原话、你的归纳。这比任何二手数据都有说服力。
