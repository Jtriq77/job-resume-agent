# 数据源、职类口径与采样方案

> 目标：岗位要**多、真、有链接、分类可评估**。不爬 BOSS 直聘登录页，不伪造岗位。
>
> **实际执行（2026-11-23）**：13 类 × 300 = 3,900 条语料；30 条带链接岗位（大/中/小各 10）；链接核验 29 ok / 1 login；详见 `data/sources.md` 与 `docs/RESULTS.md`。
> 当前数据源：**job_radar / jobsearchradar**（每日更新的中国校招、实习、社招公开岗位索引）。

---

## 1. 为什么用 job_radar，而不是直接爬 BOSS

| 维度 | 直接爬 BOSS/领英 | job_radar |
|---|---|---|
| 登录/验证码 | 需要登录，自动化通常违反平台协议 | 只索引公开可读来源，不绕过登录/验证码 |
| 链接 | 深链需登录、易失效 | 保留原始招聘链接与来源 |
| 规模 | 受账号和风控限制 | 约 36 万条岗位记录、2,172 家公司 |
| 分类 | 需自己做 | 已有 11 个职类 + 子类，可按标题规则归一 |
| 可复现 | 演示当天可能搜不到 | 固定快照 + 本地 SQLite，可复现 |
| 许可 | 平台内容版权/协议风险 | 代码 MIT；内容权利归原发布方，只做索引 |

**结论**：用 job_radar 做岗位库与链接来源；BOSS 的职类只作为产品分类参考，不直接抓取。

## 3. 职类口径（对齐 BOSS 大类）

job_radar 的 `category` 由标题规则归一，共 11 个大类。与本项目的关系：

| 职类 | 子类 | 是否本项目重点 |
|---|---|---|
| 产品 | 产品经理 | **重点**（数据/产品方向） |
| 技术 | 算法、数据、后端、前端、客户端、测试、运维、安全、嵌入式、芯片/硬件、软件开发、技术支持 | **重点**（数据方向） |
| 运营 | 运营 | **重点** |
| 设计 | 设计 | 覆盖 |
| 市场销售 | 销售、市场 | 覆盖 |
| 职能 | 人力、财务审计、法务、采购供应链、行政 | 覆盖 |
| 金融 | 投研、银行柜员、保险 | 覆盖 |
| 医药 | 医药研发、临床医学、学术推广 | 覆盖 |
| 工程制造 | 汽车工程、工艺/设备、质量、机械/电气、生产 | 覆盖 |
| 管培 | 管培生 | 覆盖 |
| 项目管理 | 项目管理 | 覆盖 |

> `category` 为空表示「标题规则没命中」，**不等于没有这类岗位**。训练时把空值单列为 `未分类` 或丢弃，报告中说明比例。

## 4. 采样方案（ML 语料 vs 链接演示集分开）

### 4.1 ML 语料：3,000–5,000 条

| 维度 | 方案 |
|---|---|
| 分层 | 11 个职类 × 约 300–400 条；产品/技术/运营可多采 |
| 类型 | 校招 60% + 实习 20% + 社招 20%（大四用户以校招/实习为主） |
| 去重 | 按 `company + title + cities` 去重；同公司同标题保留 1 条 |
| 质量 | 优先有 JD 正文（`description`/`requirements`）、标题非空、公司非空 |
| 噪声 | 保留 5%–10% 标题模糊/分类为空/短 JD，用于错误分析 |
| 链接 | ML 语料不要求都有链接；有链接的单独标记 |

**用途**：岗位族分类训练 + 匹配排序候选池。

### 4.2 链接演示集：30–40 条

| 维度 | 方案 |
|---|---|
| 公司 | 20–30 家，大/中/小各 8–12 家 |
| 岗位 | 每家公司 1–2 条，覆盖产品/数据/运营，城市以你的目标城市为主 |
| 链接 | 优先 `url_scope != unknown` 且 `availability` 可见；每条记录 `url`、`career_url`、`last_checked` |
| 兜底 | 深链 → 公司招聘主页 → 平台搜索页 |
| 核验 | 演示前手动核验；标 `ok / login_required / dead / unknown` |

**重点**：这 30–40 条是「点开就能跳」的演示集；ML 语料可以是 3,000 条，不需要都有链接。这样链接采集量从上千降到几十。

### 4.3 金标准测试集：300 条

| 项 | 方案 |
|---|---|
| 规模 | 300 条，按 11 类分层（每类约 27 条） |
| 标注 | 2 人独立标，冲突讨论；算 Cohen's κ |
| 指标 | Macro-F1、每类 P/R/F1、混淆矩阵 |
| 用途 | **只用于评估**，不参与训练；避免「用规则标签评估规则模型」的循环 |
| 失败处理 | 标注不一致的类别，报告中列为限制；必要时合并相近类 |

> 用户要求「分类训练数据要准确」：job_radar 的 `category` 是规则标签，不能假装是人工金标准。正确做法是**规则标签训练 + 300 条人工金标准评估**，报告中写清这个区别。如果 Macro-F1 不够，再人工修正 200–300 条训练样本。

## 5. 公司分层与链接

### 5.1 公司表 `companies.csv`

```csv
company_id,name,tier,industry,size_stage,city,career_url,tier_reason,verified_at
```

- 20–30 家；大/中/小各 8–12 家；
- `career_url` 优先公司官方校招主页；
- `tier_reason` 写依据（校招规模/品牌/公开规模），不写「好坏」；
- 报告加免责声明：**分层是投递节奏的主观划分，不代表公司优劣**。

### 5.2 链接状态

| 状态 | 含义 | 处理 |
|---|---|---|
| `ok` | 可打开，公开可见 | 主按钮 |
| `login_required` | 需登录/App | 标「需登录」，给公司主页兜底 |
| `dead` | 404/410/无法访问 | 切 `career_url`，再切 `search_url` |
| `unknown` | 超时/反爬/无法判断 | 不显示为主按钮，放「复制链接」 |

### 5.3 不做的事

- 不爬需要登录、验证码、付费的页面；
- 不批量再分发 job_radar 全库；
- 不把岗位内容当作已核实资格；
- 不自动提交投递。

## 6. 数据文件与脚本

```
data/
├── _raw_jobradar/          # 原始 SQLite（不提交 Git）
├── jobs_sample.jsonl       # 3,000–5,000 条 ML 语料
├── jobs_linked.jsonl       # 30–40 条带链接演示集
├── companies.csv           # 20–30 家公司 + 分层
├── link_status.csv         # 链接核验结果
├── gold_300.csv            # 300 条人工金标准
└── sources.md              # 来源、日期、许可、采样规则
```

脚本：

```bash
# 从 SQLite 分层抽样
python scripts/build_corpus.py --per-category 300 --out data/jobs_sample.jsonl

# 生成链接演示集（需先有 companies.csv）
python scripts/build_linked_set.py --limit 40 --out data/jobs_linked.jsonl

# 核验链接
python scripts/check_links.py --input data/jobs_linked.jsonl --out data/link_status.csv
```
